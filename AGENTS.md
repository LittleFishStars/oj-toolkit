# AGENTS.md

Online-judge problem authoring repo (Python-only course). Each problem generates testdata; `pack.py` bundles per-day `.zip` for upload to a judge (Hydro-style format).

## Layout
- `generator.py` — root, the shared `Generator` ABC. All problems import it.
- `pack.py` — root, per-day/per-week zip packer. Days: `python pack.py --day D1 W1D2`; whole week: `python pack.py --week W1` (or `--week` alone for all weeks); no args = pack all days.
- `Problem/Wn/Dn/P1`, `Problem/Wn/Dn/P2`, ... — problems grouped by week `Wn` then day `Dn`. Dir path segments form the problem id: cwd `.../W1/D1/P1` → `W1D1P1` (legacy flat `Problem/D1/P1` → `D1P1` also supported by `pack.py`/`gen_solution_md.py`).
- Per-problem files: `generate.py` (subclass + run), `config.yaml` (judge/checker/lang limits; Python-only: `py.py3`), `problem.yaml` (title/tags/pid), statement files matching `problem_*.md` (e.g. `problem_zh.md`), `testdata/` (generated `N.in`/`N.out`).
- Per-day artifact: `Problem/Wn/Dn/Dn.zip` (generated by `pack.py`).
- `Solution/Wn/Dn/Pn/` — mirrors `Problem/` layout; holds Python reference solutions named by pid (`W1D1P1.py`); `gen_solution_md.py` writes a `solution.md` next to them. Not used by `generate.py` or `pack.py` (each `generate.py` computes its own answer in `generate_output`); keep in sync manually.
- `Old/` — archived course material from the previous (C+Python) course; structure no longer maintained by root scripts.

## Running a generator
`Generator.generate()` reads/writes `./testdata` relative to cwd. So you MUST run from the problem dir, not the repo root. VSCode sets `PYTHONPATH=${workspaceFolder}` automatically; a bare shell needs it explicitly.

```
# From repo root:
uv run --directory Problem/W1/D1/P1 python generate.py

# Or with explicit PYTHONPATH (four levels up: P -> day -> week -> repo root):
cd Problem/W1/D1/P1 && PYTHONPATH="$(pwd)/../../../.." uv run python generate.py
```

`generate.py` creates an instance and calls `.generate()` to write `testdata/`. Class name prefix `Problem` + pid (e.g. `ProblemW1D1P1`) since class names can't start with a digit.

## Packing
Run `pack.py` from the repo root to bundle per-day zips:

```
uv run python pack.py --day D1          # match any day dir named D1 (e.g. Problem/W1/D1)
uv run python pack.py --day W1D1 W1D2   # same, using full relative-path form
uv run python pack.py                   # no args: pack every day found under Problem/
```

This creates `Problem/Wn/Dn/Dn.zip` containing all problems of that day in Hydro format:
- `{pid}/testdata/{N}.in`, `{pid}/testdata/{N}.out`
- `{pid}/testdata/config.yaml`
- `{pid}/problem.yaml`
- `{pid}/problem_*.md`

pid = the problem dir's path relative to `Problem/` joined without separators (`W1/D1/P1` → `W1D1P1`).

Generate testdata first (run each `generate.py`), then pack.

Weekly bundle: `uv run python pack.py --week W1` creates `Problem/W1/W1.zip` containing every problem of the week (same Hydro layout, pids `W1D1P1`...), ready to upload as a single batch. Day zips and the week zip are independent outputs — regenerate both after changing problems.

## Generating solution.md
`gen_solution_md.py` reads Python reference solutions from `Solution/Wn/Dn/Pn/` (`{pid}.py`) and writes a `solution.md` next to them. Accepts day args like `pack.py`:

```
uv run python gen_solution_md.py --day W1D1
```

## Generating day READMEs
`gen_day_readme.py` writes a `README.md` intro (day theme + problem table) into each day dir under `Problem/`. Day themes live in its `DAY_INTRO` dict — add an entry when creating a new day. Keys are full day ids (`W1D1`, `W2D1`) so the same `Dn` name can repeat across weeks (a bare `D1` key still works as a fallback). These READMEs are local documentation only; `pack.py` does not include them in zips.

```
uv run python gen_day_readme.py            # all days
uv run python gen_day_readme.py --day W1D1 # one day
```

## Adding a new problem
Copy an existing `Problem/W*/D*/P*` dir, rename it (this sets the pid), update the class name + logic in `generate.py`, and edit `config.yaml` / `problem.yaml` / `problem_zh.md`. `testdata/` and the `.zip` are generated output — do not hand-edit.

## Conventions / gotchas
- Managed with `uv` (Python). Note version mismatch: `pyproject.toml` requires `>=3.13` but `.python-version` pins `3.14`.
- No tests, no lint/CI configured; verification = running the generator and inspecting `testdata/` + the produced zip. Cross-check: run the `Solution/` reference program against each `testdata/*.in` and diff with `*.out`.
- `generate()` seeds `random` with the class name → regeneration is deterministic (same testdata every run); it also clears stale `.in`/`.out` and auto-provides `self._i` (0-based test index) so generators can do `i = self._i` for fixed boundary cases + random cases — no counter boilerplate needed.
- `pack.py` packs all `testdata/` files as-is; it does not use `test_num` — whatever is in `testdata/` gets packed.
- Inside the zip, `config.yaml` is placed at `<pid>/testdata/config.yaml` (not the problem root) — a Hydro layout quirk.
- `config.yaml` uses judge-specific keys (`langs` use language IDs like `py.py3`, not names; `checker_type`, `*_limit_rate`). Keep in sync with the target judge's `lang.yaml`.
